# AWS EC2 F2

The F2 port uses one openTPU slice on the slot's DDR4 DIMM, with the architecture
in `targets/f2.toml`. The small shell supplies PCIe and a 250 MHz clock;
`boards/f2/design/cl_opentpu.sv` generates phase-aligned 100 MHz core and 200 MHz
TMEM clocks. The HDK's `sh_ddr` owns DDR calibration. Its pinned `cl_ddr4` IP
uses a 938 ps DDR clock period (approximately 2133 MT/s). HBM is not instantiated
here: the HBM build (S slices of NCH pseudo-channels, 200 MHz) is docs/f2_hbm.md.

This is an initial port. Local bridge simulations and wrapper elaboration do not
establish FPGA timing closure or hardware correctness. Preserve the reports from
each Vivado run and qualify the resulting image on the dedicated openTPU slot.

## Memory and control

| Host aperture | Purpose |
|---|---|
| Application PF BAR0, first 4 KiB | openTPU control registers (OCL) |
| Application PF BAR4, `[0, 2 GiB)` | Slice 0, memory channel 0 |
| Application PF BAR4, `[2 GiB, 4 GiB)` | Slice 0, memory channel 1 |

The target exposes 4 GiB total despite the physical DIMM's larger capacity. The
native beat address is 25 bits and a beat is 64 bytes. Use the target's channel
layout when copying programs or weights; do not use another board's DDR CSR or
XDMA device path. The small shell has no XDMA engine. Host memory accesses use
PCIS through BAR4; registers use OCL through BAR0.

`otpu_f2_nch` crosses native commands/data through asynchronous FIFOs and tracks
same-beat hazards until DDR responses complete. `otpu_f2_mem` arbitrates both
channels and PCIS, preserves host AXI IDs, and blocks control writes while host
memory writes are outstanding. `otpu_axil_cdc` transfers one held OCL access at a
time into the core clock. These are in `rtl/boards/f2/`.

Virtual LED bit 0 means the core MMCM is locked, bit 1 means DDR calibration is
ready, and bits 4:2 are the board's three status LEDs. The DDR status bus uses the
HDK's eight-stage request and response pipelines.

If the core MMCM loses lock during operation, reload the AFI or apply a full
shell reset before using the device again. Lock loss resets the bridges and
discards their transaction tracking while `sh_ddr` remains active; late DDR
responses can therefore outlive that reset. Re-lock alone is not a supported
recovery path. Initial startup and a full shell reset reset both sides together.

## Host transport

After a compatible openTPU AFI is loaded and its DDR is ready, select the slot
through `OTPU_DEVICE=f2:0`, or use an explicit application PF address such as
`f2:0000:34:00.0`. `Board()` honors this variable; the chat command's `--dev`
argument overrides it.

```bash
OTPU_DEVICE=f2:0 python -m opentpu.host.chat \
  --backend board --model gemma3 --prompt "What is an FPGA?"
```

The transport requires Linux x86-64, a C compiler (`cc`), and permission to map
`resource0`, `resource4` and `resource4_wc` for the application PF. Slot discovery
uses the AWS SDK's `fpga-describe-local-image-slots`; an explicit BDF does not
require the SDK. It never loads an AFI, unbinds a driver or changes PCI settings.

BAR4 writes use the write-combining mapping, then an x86 `MFENCE` and a volatile
read from the uncached mapping in the same native helper call. The RTL's PCIS
write barrier completes earlier DDR writes before the fence read or subsequent
OCL control write is served. Raw BAR0 accesses are aligned 32-bit words.
`F2Transport(device, dma=False)` supports register reads and snapshot latching
without acquiring the exclusive execution lock or mapping BAR4.

The transport conservatively enables the existing once-per-image ECC scrub for
the exposed 4 GiB. DDR calibration alone does not establish that every ECC word
has been initialized. `BoardBackend` performs this before loading programs and
weights; allow the first startup to finish before measuring inference speed.
Code using `Board` directly must call `Board.scrub()` before payload transfers.
The `DRAM_INIT` flag avoids repeating the scrub within the same configured image.

After loading the qualified image, check its identity before running the full
hardware smoke test. The probe only reads registers and latches a snapshot; the
full test scrubs memory, writes test data and runs the accelerator:

```bash
fpga-describe-local-image -S 0 -H -M
fpga-get-virtual-led -S 0
python tools/f2_smoke.py --dev f2:0 --probe --expect-build 7e42a626 \
  --json build/f2-probe.json
timeout 600s python tools/f2_smoke.py --dev f2:0 --expect-build 7e42a626 \
  --json build/f2-smoke.json
```

LED bits 0 and 1 must both be set before the full test. Use the build ID from
the image's source manifest if it differs from this example. The test requires
the same BAR permissions as inference. `AXI_ERR` detects native DDR read/write
response errors; the current wrapper ties `ECC_DED` low, and the pinned SDK's
DDR metrics expose transaction and timeout information, not ECC error counters.
Passing the smoke test therefore does not establish ECC error observability.

## Build

Use a fresh output directory for each attempt. The launcher snapshots all RTL,
constraints and target parameters, and records their hashes plus the source
revision and working-tree status in `inputs.json`. A dirty source tree is allowed
and is explicitly recorded. It does not alter the HDK checkout.

```bash
source /path/to/Vivado/2025.2/settings64.sh
python3 boards/f2/build.py \
  --hdk /path/to/aws-fpga \
  --out build/f2-synth-001 \
  --flow SynthCL
```

`--prepare-only` creates the snapshot and `invocation.json` without starting
Vivado. `--build-id 01234567` explicitly supplies the eight-digit build identity;
the default is the source HEAD's first eight digits. The architecture hash is
computed from the target and forwarded to `CFG_HASH`.

To run synthesis and shell implementation together, use a new output directory
and `--flow BuildAll`. To reuse the verified synthesis result without changing
it, use the HDK's supported `ImplCL` path:

```bash
python3 boards/f2/build.py \
  --hdk /home/ubuntu/aws-fpga \
  --out /home/ubuntu/opentpu/build/f2-impl-001 \
  --flow ImplCL \
  --from-synth /home/ubuntu/opentpu/build/f2-synth-003 \
  --synth-sha256 1cc4e137cc672627a9f5c502aaa107f3b4a1ccef5b035b4743407b8ae3963137 \
  --package
```

`ImplCL` inherits the build ID, requires a successful parent synthesis and DDR
firmware check, verifies the expected checkpoint digest, and rejects changed
HDL, RTL parameters, platform settings or synthesis/CDC constraints. It copies
the checkpoint into a fresh run and records the parent manifest and checkpoint
hashes. Implementation scripts and placement constraints can change in the new
snapshot. The HDK links the saved checkpoint into the shell; it does not attempt
to reconstruct ELF metadata or rerun firmware initialization. The final routed
image's persisted firmware sentinel is checked again.

The build driver runs the pinned HDK Tcl directly so a
Vivado failure propagates to its exit status. It also checks for the requested
checkpoint; a `post_route.VIOLATED.dcp` is not counted as a successful routed
checkpoint. Post-route validation produces complete timing (including hold and
pulse-width), route status, bus-skew, DRC, methodology, CDC, ignored-exception,
clock-interaction and utilization reports. It requires no timing or bus-skew
violations, 14 openTPU Gray-bus constraints, both 4 ns clock-crossing bounds,
fully routed nets, and no fatal/error/critical DRC or methodology violations. Reports
are retained when validation fails; any justified waiver needs a separate
review of the actual violation rather than a blanket severity downgrade.
The current validator inspects each violation's available properties before
reading severity. If only an associated `CHECK` is available, it requires an
exact, unique rule match with a severity property. Missing properties, unknown
severity values or ambiguous rule matches fail qualification. The
`route_rule_severities.rpt` report records each resolved severity and its source
object. This hardening applies to future snapshots; the preserved
implementation 001 retains its original validator and requires independent
review of its actual DRC and methodology reports before acceptance.

If a completed routed checkpoint fails timing, an isolated post-route recovery
can be attempted after reviewing its actual critical paths. The supported
`Explore` optimization does not require resynthesis or shell relinking:

```sh
python boards/f2/route_opt.py --hdk /home/ubuntu/aws-fpga \
  --from-run build/f2-impl-001 \
  --checkpoint build/f2-impl-001/cl_opentpu/build/checkpoints/cl_opentpu.7e42a626.post_route.VIOLATED.dcp \
  --checkpoint-sha256 "$ROUTED_SHA256" --out build/f2-impl-002
```

Use the exact completed parent checkpoint path and independently verified hash.
The recovery driver requires the parent exit status, final timing report, persisted DDR
sentinel and unchanged frozen source inventory. It copies the parent's HDL and
constraints byte for byte, opens a separate checkpoint copy, and does not
reread constraints or refresh firmware. It records parent source, manifest,
log, exit-status, timing-report and checkpoint hashes alongside the recovery
driver sources. It runs post-route physical optimization, reroutes only if
routes become incomplete, and saves an unvalidated candidate before reopening
it for the full route qualification and exact firmware-sentinel comparison.
Only a qualified candidate becomes the new `post_route.dcp`. The resulting
run uses the same package-only interface below. The original run remains
unchanged. `f2-impl-002` persisted its candidate after this bounded recovery
attempt with WNS -0.051 ns, TNS -6.059 ns and WHS +0.002 ns. Its final
qualification found 280 failing setup endpoints, no hold, pulse-width,
bus-skew or route failures, and the same 38 methodology warnings. Its candidate
SHA-256 is `1fa6d14c256bd050a053b63ac202a2eab5a1a7bcde1aa16733aa8c0168005d70`.
It is not an accepted checkpoint.

For qualification of an existing routed checkpoint without physical changes,
the same driver accepts `--validate-only`. This opens the hash-verified parent
copy, runs the current qualification checks, and copies the original persisted
bytes into the accepted output only after success. It does not optimize, route,
apply constraints, or write a new checkpoint. Parent provenance and both copy
hashes are rechecked; failure removes provisional acceptance files. Always use
a fresh output directory so the original reports and checkpoint remain intact.

`--package` invokes the pinned HDK's own manifest/tarball generator only after
validation passes, then verifies that the archived checkpoint matches the
manifest and routed DCP. It also verifies the PCI IDs, shell, HDK, tool and clock
metadata. The package tag uses the HDK's timestamp format
`YYYY_MM_DD-HHMMSS` in UTC, independently of the eight-digit identity compiled
into the FPGA. Temporary timestamp aliases let the official packager produce
the correct manifest date without editing the manifest or routed checkpoint.
The generated `<timestamp>.Developer_CL.tar` contains the routed DCP and AWS
manifest, with debug probes when present. A separate
`<timestamp>.packaging.json` records the build ID, verified manifest, input and
routed-checkpoint hashes, archive hash/size, and both build-script and official
packager hashes. `outputs.json` records successful normal-build artifacts.

To package a completed run separately, provide the previously verified routed
checkpoint digest in `ROUTED_SHA256`:

```bash
python3 boards/f2/build.py --hdk /home/ubuntu/aws-fpga \
  --out /home/ubuntu/opentpu/build/f2-impl-001 \
  --package-only --route-sha256 "$ROUTED_SHA256"
```

This verifies the completed route-validation marker/log, exact checkpoint hash
and frozen source hashes. It preserves the original `outputs.json`, snapshots
and archives, and writes only a new dated archive and packaging record. It does
not rerun synthesis, implementation or firmware initialization. Any older archive
named after a hexadecimal build ID has an unsuitable manifest date and must not
be submitted; use only the verified dated archive.

Packaging does not upload artifacts, submit an AFI or program an FPGA. AFI creation needs
an approved S3 input object, accessible log prefix and `ec2:CreateFpgaImage`;
wait for the AFI to become `available` before loading its AGFI on the dedicated
slot. No implementation or AFI success is implied until those stages finish.

Outputs include:

- `console.log`, `vivado.log`, `vivado.jou`, `exit_code` and `invocation.json`.
- `cl_opentpu/build/checkpoints/cl_opentpu.<build-id>.post_synth.dcp`.
- `cl_opentpu.<build-id>.unvalidated_synth.dcp` in the same checkpoint directory
  is a recovery point for debugging later checks, not an accepted build.
- A refreshed DDR calibration BRAM check that fails if the sentinel is absent or zero.
- Synthesis hierarchy utilization, timing, CDC, bus-skew, clock-interaction and
  ignored-exception reports under
  `cl_opentpu/build/reports/`.
- With `ImplCL` or `BuildAll`, shell-linked, optimized, placed and routed
  checkpoints and qualification reports in the same tree. Successful validation
  writes `cl_opentpu.<build-id>.route_validation.passed`.

The CDC constraints bound the 250/100 MHz crossings and Gray-bus skew. They do
not group the shell and core clocks asynchronously, which would override the
max-delay bounds. Bus skew is a separate assertion, reported separately from
ordinary timing. The
100/200 MHz pair stays related and reuses `otpu_clk2x.tcl` for the pumped TMEM.
The first implementation uses the HDK's CL floorplan without custom SLR pblocks.

Before accepting an image, review timing, unconstrained endpoints, CDC and
methodology reports; check the DDR calibration firmware initialization; create
and load the AFI on the dedicated slot; then verify identity, DDR calibration,
BAR4 data round trips and the accelerator smoke test. Synthesis alone does not
perform these checks.
